# RFC: Native XPU Backend for ExecuTorch

## 🚀 The feature, motivation and pitch

### Summary

ExecuTorch already has two AOTInductor-driven backends, CUDA and Metal, built on a shared, device-agnostic foundation (`AotiPartitioner`/`AotiBackend` in `backends/aoti/`). A concrete backend only implements a handful of device-specific hooks (device name, decomposition table, compile options) on top of that shared base, plus a small C++ runtime that loads the compiled artifact and resolves AOTInductor's C-ABI symbols directly, without linking libtorch.

This RFC is to add a native Intel GPU (XPU) backend to ExecuTorch (`backends/xpu/`), following the existing AOTInductor-driven backend pattern established by CUDA and Metal. The backend compiles PyTorch models ahead-of-time via AOTInductor, targeting Intel GPUs, and executes them through ExecuTorch's lightweight, libtorch-free runtime.

Elementwise, reduction, and most other operators go through Triton, the same as on CUDA. GEMM and SDPA kernels execute through oneDNN instead, consistent with how Intel's PyTorch GPU stack already handles these ops in `torch.compile` path on XPU.

### Motivation

ExecuTorch today has no native backend for Intel GPUs. The only paths that reach Intel GPU hardware are:
- The **OpenVINO backend** - routes through Intel's proprietary OpenVINO runtime rather than PyTorch's own compiler stack.
- The **Vulkan backend** - recently extended to desktop GPUs (including Intel), but is a generic cross-vendor graphics API path, not a PyTorch/AOTInductor-native path.

PyTorch core already provides AOTInductor support for XPU, including an XPU-specific C-ABI shim (`c_shim_xpu.h`). The missing piece is the ExecuTorch-side backend: `XpuPartitioner`, `XpuBackend`, and a C++ runtime for XPU. That wires this into ExecuTorch's export/delegate/execution pipeline, matching what already exists for CUDA and Metal.

Adding this backend would:
- Bring Intel GPUs (both discrete and integrated GPUs) into ExecuTorch's supported hardware list via the same PyTorch-native compiler stack (torch.compile/AOTInductor) already used for CUDA, not a proprietary or third-party runtime.
- Be fully open-source and upstreamed into `pytorch/executorch`, since supporting Intel GPUs through the open, upstream PyTorch ecosystem is Intel's goal.

## Design summary

- `XpuPartitioner(AotiPartitioner)` - trivial port of `CudaPartitioner` (`target_device="xpu:0"`).
- `XpuBackend(AotiBackend)` - reuses `preprocess()` unchanged; implements `get_device_name()→"xpu"`, a decomposition table, and XPU-specific custom passes.
- **GEMM / SDPA path:** new, minimal C-shim implementations written directly against oneDNN's primitive API, matching the existing `c_shim_xpu.h` function signatures for drop-in compatibility, but without linking `libtorch_xpu.so`. This is the backend's permanent, strategic kernel path for GEMM/SDPA, not an interim measure.
- **Elementwise / reduction path:** Triton-generated kernels, embedded into the compiled `.so` via `aot_inductor.embed_kernel_binary`, exactly as on CUDA.
- `aoti_delegate_handle.h` reused unchanged (already device-agnostic).
- **Tensor representation** - follow CUDA's `SlimTensor` path.
- **XPU prerequisites:**
  - add `XPU` to ExecuTorch's own serialization schema (`exir/schema.DeviceType`, `schema/program.fbs`, and the runtime-side `runtime/core/portable_type/device.h` mirror)
  - add `DeviceType::XPU` support to `backends/aoti/slim/c10/core/Device.h`.
  - register a `DeviceAllocator` for `DeviceType::XPU` (`runtime/core/device_allocator.h`), mirroring `backends/cuda/runtime/cuda_backend.cpp`'s `CudaAllocator` registration.

### oneDNN dependency for XPU

CUDA's backend routes GEMM/conv through Triton exclusively to stay libtorch-free. Any fallback to a non-Triton implementation would pull in `libtorch_cuda.so`'s ATen backend (and cuBLAS with it). Triton's Intel XPU backend does not currently support GEMM templates, so that same Triton-only strategy isn't available for XPU today. Instead, GEMM and SDPA on XPU are expected to run through oneDNN, consistent with how Intel's PyTorch GPU stack already uses oneDNN for these ops elsewhere.

PyTorch core's autogenerated `c_shim_xpu.h` already exposes GEMM, convolution, and SDPA C-ABI entries backed by ATen's XPU implementation (which itself calls oneDNN), but calling those shims as-is means linking `libtorch_xpu.so`, the exact class of heavy dependency this design wants to avoid. The plan is for ExecuTorch to provide its own minimal shim implementations, matching the same function signatures, that call oneDNN's primitive API directly instead of going through ATen/`libtorch_xpu.so`.

For packaging, the plan is to statically link a standalone, GPU-targeted oneDNN build directly into ExecuTorch's XPU runtime, following the same build recipe PyTorch itself already uses to produce oneDNN for `libtorch_xpu.so` (`cmake/Modules/FindMKLDNN.cmake`), a self-contained artifact with no dependency on a pre-installed system oneDNN.

## Scope

This backend's primary near-term targets are Intel integrated GPUs (e.g. Arc Graphics on Core Ultra/Panther Lake) serving edge-AI and on-device laptop scenarios.

### Windows PoC with XPU backend

Since this RFC was drafted, a hands-on PoC has been built and validated end-to-end on real Intel GPU hardware (integrated Arc Graphics) on Windows. **Confirmed working:** export → `AotiBackend.preprocess()`/`torch._inductor.aot_compile()` → a real Windows DLL → device memory allocation → Triton-XPU kernel launch → correct numerical result, for a trivial elementwise `add` model. This validates the overall `AotiBackend`/`AotiPartitioner` reuse strategy and the Triton/elementwise path described above.

Few of the findings below are Windows-specific, but the overall architecture applies to Intel integrated GPUs generally.

- **Windows needs a real, separate runtime shim DLL**, mirroring CUDA's own two-tier mechanism (a compile-time-only stub import library for the AOTInductor compile step, plus a real shared library loaded at actual runtime). Linux/macOS don't need this: a loaded module's unresolved symbols there can resolve against anything already loaded in-process.
- **XPU's Triton kernel-launch path needs extra bridging** - three raw `c10::xpu::*` symbols that translate an abstract `sycl::device`/`context` down to native Level-Zero handles. This same device/queue/context plumbing is likely reusable for the oneDNN GEMM path too.

### Proposed phasing

1. **Prerequisites** - land the small, mechanical ExecuTorch-side patches: `XPU` in the serialization schema (`exir/schema.DeviceType`, `program.fbs`), `DeviceType::XPU` in `backends/aoti/slim/c10/core/Device.h`, and an `XpuAllocator` registered for `DeviceType::XPU`.
2. **Elementwise/Triton path** - `XpuPartitioner`/`XpuBackend` plus the SlimTensor-based runtime (device guard, memory shims, Windows shim DLL), validated end-to-end on a simple model on Intel integrated GPU hardware.
3. **GEMM / SDPA via oneDNN** - the C-shim implementations against oneDNN's primitive API, validated against models with `mm`/`addmm`/SDPA layers (e.g. a small transformer block). This is the RFC's core, unproven claim and the highest-risk phase.
4. **Hardening** - weights/constants blob handling, multi-method export, broader op coverage, and Linux support.
