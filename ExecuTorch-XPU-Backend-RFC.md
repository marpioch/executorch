## PoC validation status (update)

Since this RFC was drafted, a hands-on PoC (`backends/xpu/`, branch `xpu-backend`) has been built and validated end-to-end on real Intel GPU hardware (Panther Lake integrated Arc Graphics, Windows). **Confirmed working:** export → `AotiBackend.preprocess()`/`torch._inductor.aot_compile()` → a real Windows DLL → device memory allocation → Triton-XPU kernel launch → correct numerical result, for a trivial elementwise `add` model. This validates the overall `AotiBackend`/`AotiPartitioner` reuse strategy and the Triton/elementwise path described below.

**Not yet validated by the PoC:** the GEMM/SDPA-via-oneDNN proposal that is this RFC's central design question — the PoC never exercised `mm`/`addmm`/SDPA. Everything below marked "PoC finding"/"PoC-confirmed" is a concrete, hands-on-confirmed fact from getting the elementwise path working; everything about oneDNN/GEMM below remains the original research-based proposal, unchanged and still open.

The PoC also surfaced several Windows-specific architecture requirements this RFC didn't originally address, and one correction to the "Known gap" below (the PoC did not end up needing the SlimTensor device-parsing patch, for reasons explained in the new section further down). See **"PoC findings: Windows-specific runtime architecture"** for details.

## 🚀 The feature, motivation and pitch

### Summary

Add a native Intel GPU (XPU) backend to ExecuTorch (`backends/xpu/`), following the existing AOTInductor-driven backend pattern established by CUDA and Metal. The backend compiles PyTorch models ahead-of-time via AOTInductor, targeting Intel GPUs, and executes them through ExecuTorch's lightweight, libtorch-free runtime.

This RFC proposes a backend design that takes a direct, permanent dependency on oneDNN for GEMM and SDPA kernels. Unlike the CUDA backend — which forces all GEMM/conv through Triton specifically to avoid any vendor math library dependency — this is a deliberate, long-term architectural choice for Intel GPU, not an interim workaround: Intel's PyTorch GPU strategy already relies on oneDNN as the primary, actively maintained kernel backend for GEMM/SDPA across the stack (including the `torch.compile`/Inductor path on eager XPU), and the ExecuTorch backend should be consistent with that strategy rather than attempt to avoid it. Elementwise/reduction ops continue to go through Triton, as they already do for CUDA.

### Motivation

ExecuTorch today has no native backend for Intel GPUs. The only paths that reach Intel GPU hardware are:
- The **OpenVINO backend** — routes through Intel's proprietary OpenVINO runtime rather than PyTorch's own compiler stack.
- The **Vulkan backend** — recently extended to desktop GPUs (including Intel), but is a generic cross-vendor graphics API path, not a PyTorch/AOTInductor-native path.

Meanwhile, PyTorch core already treats XPU as a first-class AOTInductor target:
- `c_shim_xpu.h` — an autogenerated, XPU-specific AOTInductor C-ABI shim, present alongside `c_shim_cpu.h`/`c_shim_mps.h`.
- `AOTIModelContainerRunnerXpu` — a libtorch-level convenience runner class analogous to `AOTIModelContainerRunnerCuda`, confirmed present in `pytorch/pytorch` main.
- A `shim_symbol_prefix` mechanism (PR #190922) explicitly designed to let a backend (ExecuTorch's "SlimTensor" is the named example) ship its own `aoti_torch_*` shim implementations disjoint from libtorch's — enabling libtorch-free coexistence.

This means the foundational AOTInductor+XPU codegen path already exists in PyTorch core; the missing piece is the ExecuTorch-side backend (`Partitioner` + `BackendDetails` + C++ runtime) that wires it into ExecuTorch's export/delegate/execution pipeline, matching what already exists for CUDA and Metal.

Adding this backend would:
- Bring Intel GPUs (Arc, Data Center Max, integrated Arc Graphics on Core Ultra/Panther Lake) into ExecuTorch's supported hardware list via the same PyTorch-native compiler stack (torch.compile/AOTInductor) already used for CUDA — not a proprietary or third-party runtime.
- Extend the team's existing PyTorch XPU enablement work (torch.compile, Windows XPU, distributed, quantization) into the edge/on-device inference space, where interest in running smaller/quantized models locally is growing quickly (on-device GenAI assistants, real-time vision/audio, AI PC scenarios).
- Be fully open-source and upstreamed into `pytorch/executorch`, consistent with the team's broader strategy of driving Intel GPU support through the open PyTorch ecosystem rather than a closed/proprietary stack.

## Background: How AOTI-driven ExecuTorch backends work today

Every AOTI-driven backend (CUDA, Metal) is built from two shared, device-agnostic base classes:

- **`AotiPartitioner`** (`backends/aoti/aoti_partitioner.py`) — FX graph partitioning via `CapabilityBasedPartitioner`; tags delegated nodes; skips ATen decomposition for delegated ops. Concrete backends subclass this only to inject a `target_device` CompileSpec (e.g. `CudaPartitioner` sets `"cuda:0"`).
- **`AotiBackend`** (`backends/aoti/aoti_backend.py`) — an abstract mixin whose `preprocess()` method is the single, shared compile-time pipeline used by every concrete backend:
  1. `get_device_name()` → device string
  2. `move_program_to_device()` — moves params/buffers to that device
  3. `ReplaceViewCopyWithViewPass` + `get_custom_passes()` — graph rewrites
  4. `get_decomposition_table()` → `run_decompositions()`
  5. `get_supported_fallback_kernels()` gates `collect_unsupported_fallback_kernels()`
  6. **`torch._inductor.aot_compile(module, inputs, options=get_aoti_compile_options())`** — the actual AOTInductor compile call
  7. `materialize_weights_blob()`, `codesign_so()`, `load_weights_blob()`, `save_data_externally()` — packaging into the `.pte`/`.ptd`
  8. `release_moved_tensors()` — frees device memory before the next method's compile

A concrete backend only needs to implement 4 abstract methods (`get_device_name`, `get_supported_fallback_kernels`, `get_decomposition_table`, `get_aoti_compile_options`) plus optional hooks — **all of `preprocess()`'s orchestration is reused unchanged**.

On the runtime side, ExecuTorch's `CudaBackend` (C++) does **not** use libtorch's `AOTIModelContainerRunnerCuda`. It reimplements the minimal loading logic itself: `dlopen`s the compiled `.so`, resolves the raw AOTInductor C-ABI symbols (`AOTInductorModelContainerCreateWithDevice`, `...Run`, etc.) directly, and wraps tensors using ExecuTorch's own lightweight **`SlimTensor`** type instead of libtorch's `at::Tensor`. This is precisely how ExecuTorch achieves "libtorch-free execution" — it never links `libtorch`/`AOTIModelContainerRunner*` at runtime.

`backends/aoti/aoti_delegate_handle.h`, which defines the raw C-ABI function pointer types used for this dlopen-based loading, is **already fully device-agnostic** and directly reusable for XPU with no changes.

**Known gap found during research:** ExecuTorch's `SlimTensor` device layer (`backends/aoti/slim/c10/core/Device.h`) currently only parses `"cpu"`/`"cuda"` device strings. A small, mechanical patch adding `DeviceType::XPU` and `"xpu"`/`"xpu:N"` string parsing is a required prerequisite before any XPU delegate handle can represent an XPU tensor.

**PoC update:** the PoC sidestepped this gap entirely by not using `SlimTensor` at all — it uses ExecuTorch's plain ETensor (`executorch::runtime::etensor::Tensor`) via `backends/aoti/common_shims.cpp` (`aoti_common`), the same device-agnostic shim library the **Metal** backend uses, rather than the SlimTensor-based `aoti_common_shims_slim` CUDA uses. This was simpler to stand up and avoided the `Device.h` patch above, but it is a real architectural fork in the road for the production backend — see the new design-choice discussion and open question further down.

A second, separate schema-level gap was also found, unrelated to SlimTensor: ExecuTorch's own serialization schema (`exir/schema.DeviceType`, `schema/program.fbs`) only defines `CPU`/`CUDA`. `PropagateDevicePass` rejects a `"xpu"` target-device compile spec until `XPU` is added there too. This is a prerequisite regardless of which tensor representation (SlimTensor or ETensor) the production backend ultimately uses.

## PoC findings: Windows-specific runtime architecture

The PoC's target hardware (integrated Arc Graphics on Panther Lake) is, in practice, predominantly **Windows** hardware — the "AI PC" scenarios this RFC's motivation section calls out are Windows laptops. The original RFC draft did not address Windows as a platform concern at all; the PoC was built and validated exclusively on Windows and surfaced several requirements worth folding into the design before implementation begins in earnest.

### Windows requires a real, separate, named shim DLL — Linux does not

On Linux, a `dlopen`'d shared object's unresolved symbols can be satisfied by anything already loaded in the same process (e.g. via `-Wl,--export-dynamic` on the final executable) — this is how Metal's `metal_backend` (a *static* library, no separate `.dylib`) and CUDA's Linux build get away without shipping a dedicated runtime shim DLL. **Windows has no equivalent mechanism.** Every import in a DLL's import table is bound to one specific, named module at link time; there is no "resolve against whatever loaded me" fallback.

CUDA's own Windows support (confirmed by reading `backends/cuda/runtime/aoti_cuda_shims.lib.md` and `cuda_backend.py`) already works around this with a two-artifact split:
- `aoti_cuda_shims.lib` — a hand-built, **compile-time-only** stub import library (built via MinGW's `dlltool`, zero real code), checked into git, used only so `torch._inductor.aot_compile()`'s linker can resolve the generated wrapper's imports when lowering *for* Windows (typically done as a cross-compile from Linux CI).
- `aoti_cuda_shims.dll` — the *real* shared library (`add_library(aoti_cuda_shims SHARED ...)`), built from CUDA-specific shims + `aoti_common_shims_slim`, shipped separately for actual runtime loading on a Windows+NVIDIA machine.

The PoC mirrors this same two-tier split for XPU (`xpu_shims.def`/`.lib` as the compile-time stub, a real `xpu_shims` `SHARED` CMake target as the runtime DLL — built from `xpu_guard.cpp`, `xpu_functions.cpp`, `xpu_tensor_attribute.cpp`, `xpu_memory.cpp`, linked against `aoti_common`). One difference: since oneAPI/SYCL has no realistic Linux-cross-compile-to-Windows story the way MinGW+nvcc does for CUDA, the PoC's lowering and execution both happen natively on the same Windows+Intel-GPU machine — simpler than CUDA's split Linux-build/Windows-run model, with no cross-compilation step at all.

### XPU's kernel-launch path needs extra bridging that CUDA's doesn't

AOTInductor's generated Triton-XPU kernel-launch wrapper code calls three raw, C++-mangled symbols directly — `c10::xpu::current_device()`, `c10::xpu::get_raw_device()`, `c10::xpu::get_device_context()` — bypassing the `aoti_torch_*` C-ABI shim entirely. These bridge an abstract `sycl::device`/`sycl::context` down to native Level-Zero handles for `zeModuleCreate`/`zeKernelCreate`. **CUDA's equivalent kernel-launch path needs no such bridging** — it talks to the CUDA Driver API directly from a `cudaStream_t`. This is a genuine asymmetry in upstream PyTorch's current AOTI implementation for XPU (SYCL is a backend-agnostic abstraction; CUDA's driver API is not), not a gap in ExecuTorch's design. The PoC implements a small, libtorch-free device pool + shared `sycl::context` (mirroring `c10/xpu/XPUFunctions.cpp`'s own logic) to supply these three symbols for real.

**This same device-pool/queue/context plumbing is very likely required infrastructure for the oneDNN GEMM path proposed below too** — `dnnl::sycl_interop::make_engine()`/`make_stream()` need exactly the same `sycl::device`/`sycl::context` acquisition this PoC already built for Triton kernel launches. This is a concrete, reusable piece of groundwork this RFC's GEMM implementation can build on rather than re-derive.

### MSVC exports nothing from a DLL by default

Unlike Linux/macOS, every single symbol crossing the `xpu_shims.dll` boundary — including plain C++ helper functions that are *not* part of the `aoti_torch_*` contract (e.g. an internal `get_or_create_xpu_queue()` helper called from the backend's own `execute()`) — needs an explicit `__declspec(dllexport)`/`dllimport` pair (`AOTI_SHIM_EXPORT` in `backends/aoti/export.h`), or the final link fails with `LNK2019`. Easy to miss piecemeal; worth designing the shim library's export surface deliberately up front rather than discovering missing exports one `LNK2019` at a time (as the PoC did).

### A torch upstream bug specific to the native-Windows + `cross_target_platform="windows"` combination

`torch/_inductor/cpp_builder.py`'s `get_cpp_options()` checks `config.aot_inductor.cross_target_platform == "windows"` alone (unlike `get_cpp_compiler()`, which correctly also checks `sys.platform != "win32"`), so it unconditionally probes for a MinGW cross-compiler (`x86_64-w64-mingw32-g++`) that doesn't exist on a native Windows host. This confirms the `cross_target_platform="windows"` mechanism (the same one CUDA's Windows support uses) was designed around genuine Linux→Windows cross-compilation, not the native-Windows lowering this PoC does. Workaround used: a temporary monkeypatch scoped through `get_extra_aoti_compile_context_manager()` — the same extensibility hook `CudaBackend` itself already uses for its own upstream workarounds, so no change to shared ExecuTorch code was needed, just a backend-specific context manager.

### Two shared-base-class (`AotiBackend`) bugs, not XPU-specific, found by first real use on Windows

Both below live in `backends/aoti/aoti_backend.py` (shared across all AOTI backends) and were never previously exercised because CUDA/Metal are Linux/macOS-only in practice:
- `preprocess()` hardcoded the compiled artifact's expected extension as `.wrapper.so`. Native Windows AOTInductor codegen actually emits `.wrapper.pyd`. Fixed to accept `.so`/`.pyd`/`.dll`.
- `preprocess()` unconditionally required a weights blob file to exist. A parameter-free model (like the PoC's `add`) produces none (AOTI only emits one when `aot_inductor.package_constants_on_disk_format` is set, which CUDA does but this PoC does not). Fixed to treat a missing blob as empty, rather than erroring.

### ExecuTorch's own memory planner needs a registered `DeviceAllocator`, separate from the shim DLL entirely

Unrelated to the AOTI/shim-library story above: ExecuTorch's device-aware memory planner (`exir/passes/propagate_device_pass.py` + `runtime/core/device_allocator.h`) allocates every non-CPU-tagged planned buffer through a `DeviceAllocator` looked up by `DeviceType` in a global registry. Nothing registers one for XPU by default — `Method::init()` fails with `"No device allocator registered for device type 2"` otherwise. The PoC adds a minimal `XpuAllocator` (SYCL USM-backed `malloc_shared`/`free`) registered at static-init time, mirroring exactly how `backends/cuda/runtime/cuda_backend.cpp` registers `CudaAllocator`. This is required for **any** XPU backend design, independent of the SlimTensor-vs-ETensor or oneDNN-vs-Triton questions below.

### The backend's `execute()` cannot pass raw caller tensors into `Run()` — a correctness bug invisible until real hardware

AOTInductor's generated code treats every `AtenTensorHandle` it's given as RAII-owned: it calls `aoti_torch_delete_tensor_object` on input handles once `Run()` is done with them, and may replace output handles with its own. A naive `execute()` that hands the caller's raw tensor pointers straight to `Run()` **compiles, links, and loads correctly**, and only fails at actual model-execution time with an opaque "tensor not found" error from inside the cleanup path — this was only caught by testing on real hardware. The fix (and the correct general pattern): wrap every input/output tensor via `aoti_torch_empty_strided` + a `aoti_torch_copy_` shim before calling `Run()`, then copy results back out afterward — exactly what `backends/apple/metal/runtime/metal_backend.cpp`'s `execute()` already does. (CUDA's `execute()` is harder to use as a reference here since it's built around SlimTensor rather than plain ETensor.)

### Platform risk: AOTInductor's Windows support is immature

Externally confirmed by an Intel architect working on PyTorch, independent of this PoC: **"AOTI does not support Windows, or its Windows support is very limited."** The PoC's own findings corroborate this directly, with concrete upstream evidence beyond our own deductions:

- `torch/_inductor/cpp_builder.py` contains `get_ld_and_objcopy()`, which **unconditionally raises `"Windows is not supported yet."`** on Windows. This is the kernel-binary-embedding path behind `aot_inductor.embed_kernel_binary` (used by both CUDA's and this RFC's proposed design); its only call site in `codecache.py` is defensively gated behind `if not _IS_WINDOWS`, i.e. upstream explicitly carves Windows out of this feature rather than supporting it.
- The MinGW cross-compiler probe bug described above (`get_cpp_options()` doesn't gate its MinGW check behind `sys.platform != "win32"` the way `get_cpp_compiler()` correctly does) is itself evidence that the **native-Windows + `cross_target_platform="windows"` combination this PoC exercises is essentially untested upstream** — CUDA's own usage of that same flag is a Linux-hosted cross-compile, a materially different code path that would never trip this bug.
- Two bugs found in ExecuTorch's own shared `AotiBackend` code (the `.wrapper.so` extension hardcoding, the unconditional weights-blob requirement) had simply never been exercised on Windows before, for any backend — further evidence that native-Windows AOTI compilation is a largely unvalidated path even within ExecuTorch itself, not just upstream PyTorch.

**Net assessment:** the mechanism is reachable — this PoC got a trivial elementwise model compiling and running correctly end-to-end, natively, on Windows — but only after finding and fixing/working around several real gaps along the way. That is "reachable with targeted fixes," not "mature/supported." Nothing about GEMM/SDPA or more complex models has been exercised on Windows, so this assessment should not be extrapolated beyond the narrow scope actually tested. This materially informs open question 5 below (whether Windows should be a first-class, primary target from the start) and is a genuine schedule/scope risk for any phase of this RFC that assumes native-Windows AOTI compilation works out of the box.

## Why this design needs a oneDNN dependency

CUDA's backend forces all GEMM/conv through Triton exclusively:

```python
"max_autotune_gemm_backends": "TRITON",
"max_autotune_conv_backends": "TRITON",
"aot_inductor.link_libtorch": False,
"aot_inductor.embed_kernel_binary": True,
```

This is not just a performance choice — it is *required* to stay libtorch-free. Any fallback to a non-Triton GEMM implementation would call into `libtorch_cuda.so`'s ATen XPU/CUDA backend (which embeds cuBLAS), a large dependency CUDA's backend avoids entirely.

**Triton's Intel XPU backend does not currently support GEMM templates, and this is not treated as a temporary gap to work around.** GEMM (`mm`/`addmm`/`bmm`) and SDPA on XPU are expected to run through oneDNN as the primary, strategic kernel path — consistent with how oneDNN is already used across Intel's PyTorch GPU stack, including the `torch.compile`/Inductor path today. This design accepts that dependency deliberately rather than treating it as something to eventually eliminate.

### Confirmed: `c_shim_xpu.h` already exposes the relevant ops

Direct inspection of PyTorch core's autogenerated `torch/csrc/inductor/aoti_torch/generated/c_shim_xpu.h` confirms XPU-specific C-ABI entries already exist for:

- **GEMM / matmul family:** `aoti_torch_xpu_addmm_out`, `aoti_torch_xpu_bmm_out`, `aoti_torch_xpu_baddbmm_out`, `aoti_torch_xpu_addbmm`, `aoti_torch_xpu_addmv`, `aoti_torch_xpu__addmm_activation`, `aoti_torch_xpu__scaled_mm`, `aoti_torch_xpu__scaled_mm_out`, `aoti_torch_xpu__int_mm_out`, `aoti_torch_xpu__weight_int4pack_mm`, `aoti_torch_xpu__weight_int8pack_mm`
- **Convolution:** `aoti_torch_xpu_convolution`, `aoti_torch_xpu_convolution_backward`
- **SDPA / Flash Attention:** `aoti_torch_xpu__scaled_dot_product_flash_attention`, `aoti_torch_xpu__scaled_dot_product_flash_attention_backward`, `aoti_torch_xpu__scaled_dot_product_efficient_attention` (+ `_backward`), `aoti_torch_xpu__scaled_dot_product_fused_attention_overrideable` (+ `_backward`)

These entries confirm ATen's XPU backend (already internally backed by oneDNN) is reachable through the stable AOTInductor C-ABI today.

**The nuance that drives this design:** calling these shims as-is means linking against `libtorch_xpu.so` — the full ATen XPU backend library, with oneDNN calls buried inside it. That is the exact class of heavy dependency the CUDA backend's Triton-only strategy exists to avoid, and it remains something this design wants to avoid too, even while depending directly on oneDNN. To keep the backend libtorch-free while still using oneDNN, ExecuTorch needs **its own** minimal shim implementations, matching the same function signatures, that call oneDNN's primitive API directly — not the `libtorch_xpu.so` path. In other words: depend on oneDNN directly, not on libtorch's wrapping of oneDNN.

### oneDNN bundling strategy

PyTorch's own build already has a proven recipe for building a standalone, GPU-targeted oneDNN (`cmake/Modules/FindMKLDNN.cmake`, `xpu_mkldnn_proj`):

```cmake
ExternalProject_Add(xpu_mkldnn_proj
  GIT_REPOSITORY https://github.com/uxlfoundation/oneDNN
  GIT_TAG v3.12.3
  CMAKE_ARGS
    -DDNNL_GPU_RUNTIME=SYCL
    -DDNNL_CPU_RUNTIME=NONE
    -DDNNL_LIBRARY_TYPE=STATIC
    -DONEDNN_BUILD_GRAPH=ON
  ...
)
```

producing a static library (`libdnnl.a` on Linux, `dnnl.lib` on Windows), which PyTorch itself statically links into `libtorch_xpu.so`.

**Proposed approach for ExecuTorch:** adapt this same recipe into `backends/xpu/CMakeLists.txt` (modeled on `backends/cuda/CMakeLists.txt`'s CUDA toolkit discovery pattern) and **statically link** a standalone oneDNN build directly into ExecuTorch's XPU runtime shared library.

- **Why static-link (vs. dynamic/system):** matches the CUDA backend's "self-contained artifact" philosophy — no assumption of a pre-installed vendor stack on the target machine, no separate runtime artifact to distribute, no version-mismatch risk against whatever oneDNN a user's system happens to have.
- **Trade-offs to accept:** increases the compiled runtime's binary size; requires the DPC++/icx toolchain to be available at ExecuTorch build time (already a requirement for any XPU PyTorch build, so no new build-environment burden).
- **Alternative considered — dynamic/shared oneDNN library shipped alongside the runtime:** smaller main binary, but adds a second artifact to package/version/ship and a real ABI-compatibility surface to maintain; rejected in favor of the simpler, proven static-link model.
- **Alternative considered — rely on a system-installed oneDNN:** lowest packaging effort, but reintroduces exactly the kind of environment-dependency risk the libtorch-free design is meant to avoid; rejected.

### Design summary

- `XpuPartitioner(AotiPartitioner)` — trivial port of `CudaPartitioner` (`target_device="xpu:0"`); **PoC-confirmed.**
- `XpuBackend(AotiBackend)` — reuses `preprocess()` unchanged; implements `get_device_name()→"xpu"`, a decomposition table, and XPU-specific custom passes; **PoC-confirmed** (including a Windows-only `get_extra_aoti_compile_context_manager()` override for the MinGW-probe workaround above).
- **GEMM / SDPA path:** new, minimal C-shim implementations written directly against oneDNN's primitive API, matching the existing `c_shim_xpu.h` function signatures for drop-in compatibility, but without linking `libtorch_xpu.so`. This is the backend's permanent, strategic kernel path for GEMM/SDPA, not an interim measure. **Not yet validated** — the PoC did not implement or test this path. The device-pool/queue/context plumbing built for the elementwise path below is expected to be directly reusable here (see "PoC findings" above).
- **Elementwise / reduction path:** Triton-generated kernels, embedded into the compiled `.so` via `aot_inductor.embed_kernel_binary`, exactly as on CUDA. **PoC-confirmed end-to-end** on real hardware, including the extra `c10::xpu::*` kernel-launch bridging described above.
- `get_aoti_compile_options()` must **not** set `max_autotune_gemm_backends="TRITON"` (no template exists, and none is required); GEMM ops are explicitly allowed in `get_supported_fallback_kernels()`
- `aoti_delegate_handle.h` reused unchanged (already device-agnostic); **PoC-confirmed.**
- **Tensor representation — open design choice, not yet settled:** the PoC uses ExecuTorch's plain ETensor (via `aoti_common`/`common_shims.cpp`, Metal's approach) rather than `SlimTensor`, and so did not need the `Device.h` patch below. Whether the production backend should follow CUDA's `SlimTensor` path instead (e.g. for GPU-resident intermediate tensors, parity with CUDA's device-aware memory planning, or future perf work) or stay with the simpler ETensor approach is an open question — see below.
- Prerequisite patch (only if `SlimTensor` is chosen): add `DeviceType::XPU` support to `backends/aoti/slim/c10/core/Device.h`.
- **New prerequisite patch found by the PoC, required regardless of tensor representation:** add `XPU` to ExecuTorch's own serialization schema (`exir/schema.DeviceType`, `schema/program.fbs`, and the runtime-side `runtime/core/portable_type/device.h` mirror) — currently only `CPU`/`CUDA` are defined, and `PropagateDevicePass` rejects a `"xpu"` compile spec without it.
- **New prerequisite found by the PoC:** register a `DeviceAllocator` for `DeviceType::XPU` (`runtime/core/device_allocator.h`), mirroring `backends/cuda/runtime/cuda_backend.cpp`'s `CudaAllocator` registration — otherwise device-aware memory planning fails at `Method::init()` regardless of how GEMM/elementwise kernels are implemented.
- **New requirement found by the PoC (Windows only):** a real, separate, named runtime shim DLL (`xpu_shims.dll`) plus a compile-time-only stub import library, per "PoC findings" above — not needed on Linux/macOS, where the existing Metal/CUDA `-export_dynamic` pattern suffices.
- SYCL-TLA is out of scope for this design. It remains a relevant, complementary kernel backend investment elsewhere in the team's broader PyTorch XPU compiler work, but this backend does not depend on it, and adopting it later would be a separate proposal rather than a planned phase of this one.

## Alternatives considered

- **Out-of-tree vendor backend repository** (e.g. `xpu-executorch-backend`), per the pattern proposed in ExecuTorch RFC #20975 ("First-class support and reference implementation for out-of-tree backends"). Rejected for this proposal in favor of in-tree (`backends/xpu/`), consistent with the team's strategy of open, upstream, community-visible contribution rather than a separately maintained fork — matching the precedent set by the in-tree CUDA and Metal backends.
- **Force GEMM/SDPA through Triton only, matching CUDA's model exactly, and treat oneDNN as unsupported.** Rejected: Triton's Intel XPU backend has no GEMM templates today, and pursuing Triton-only GEMM would run counter to Intel's broader PyTorch GPU strategy, which already relies on oneDNN as the primary kernel backend for these ops. Forcing this would also block delivery indefinitely on an external, uncontrolled dependency.
- **Rely on system-installed oneDNN instead of static-linking.** Rejected; see bundling strategy discussion above.

## Open questions for reviewers

1. Is a statically-linked, direct oneDNN dependency an acceptable, permanent part of a backend described as "libtorch-free," given it depends on oneDNN directly rather than through ATen/libtorch_xpu.so?
2. In-tree (`backends/xpu/`) vs. out-of-tree vendor repository, given the open discussion in RFC #20975?
3. Should the GEMM/SDPA C-shim implementations aim for bit-exact parity with `libtorch_xpu.so`'s ATen-dispatched results, or is numerical parity within normal tolerance sufficient given they call oneDNN directly rather than through ATen?
4. **Tensor representation: `SlimTensor` (CUDA's approach) or plain ETensor (Metal's approach, and what the PoC used)?** The PoC found ETensor materially simpler to stand up (reuses `aoti_common`'s existing generic shims as-is, no `Device.h` patch needed) but SlimTensor is CUDA's established pattern and may matter for future device-resident-tensor/perf work. Worth deciding deliberately rather than defaulting to whichever was easier to prototype.
5. **Should Windows be treated as a first-class, primary target from the start of implementation**, given the RFC's own named hardware (integrated Arc Graphics on Core Ultra/Panther Lake, "AI PC" scenarios) is predominantly Windows laptop hardware, and Windows requires materially more runtime-shim-library infrastructure than Linux/macOS (see "PoC findings" above)? See also "Platform risk: AOTInductor's Windows support is immature" above — externally confirmed by an Intel PyTorch architect and corroborated by concrete upstream evidence found during the PoC.
